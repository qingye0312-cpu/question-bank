# 三端统一题库格式与加密评估

日期：2026-10-15。依据用户批注：先内置题库，三端格式要统一并考虑加密；云暂缓、以后优先腾讯；下载权限之后确定。

状态：统一内容与小程序本地索引已落地；加密、签名、授权发钥和联网更新是后续设计，当前没有启用。当前工程内含可读取的题目明文，适合本机开发与体验验证。

## 1. 推荐方案

采用“三端同一内容包，各端独立搜索索引，可选统一加密外层”。沿用现有 `.qbank.zip` v1，不新增一套手机题目模型，也不把手机索引塞入 v1 包中。

| 方案 | 三端复用与迁移 | 评价 |
| --- | --- | --- |
| 直接共用桌面 SQLite 文件 | 桌面容易，小程序需要额外数据库运行时，涉及 FTS5 和文件兼容 | 不选作交换格式 |
| 桌面包与 `.qbank.mobile.zip` 各带题目 | 内容可以保持一致，但增加重复制包和同步校验责任 | 可以实现，当前没有必要 |
| 同一 `.qbank.zip`＋索引配套文件 | 现有 Mac／Windows 已支持内容包；小程序复用题目、ID、答案和哈希，单独加载索引 | 推荐，当前内置版已使用同一内容 |
| 全部改为加密的新 v2 包 | 可以设计统一容器，但旧客户端均需升级，密钥策略尚未明确 | 后续用加密外层逐步接入，不直接破坏 v1 |

统一内容与统一运行数据库是两件事。Mac／Windows 继续把标准内容导入本地 SQLite，手机读取 JSONL 和倒排索引；最终题目与答案来自相同发布内容。

## 2. 内容协议和当前实现

标准内容包保持只含：

```text
bank.qbank.zip
  manifest.json
  questions.jsonl
```

三端统一 `bank_id`、`release_version`、`release_id`、题目 ID、选项 ID、题目顺序、原始题文和答案。`release_id` 继续是 `questions.jsonl` 原始字节的 SHA-256；文件编码、换行、字段顺序改变也会改变它，因此发布一次后不在客户端重新序列化来计算内容身份。

当前小程序代码包内置标准包解出的两个文件，以及额外的 `data/index.json`。索引记录 `schema_version=qbank-index-1`、`release_id` 和 `question_count`，绑定同一份内容。索引的单字／双字 posting 使用差分数字的 base36 字符串减少体积；这只是压缩编码，不是加密。

构建工具默认从桌面内置源 `src-tauri/resources/seed.json` 生成，并匹配桌面 Rust 序列化顺序与默认字段；已与桌面 `qbank-tool export-seed` 输出逐字节比较。也支持读取已解压的标准包，校验清单、大小、哈希和题数，再原样拷贝 JSONL。不能宣称读取了维护者本机数据库中未导出的新修改。

未来网络发布可用下面的布局，索引不是 v1 ZIP 的第三个成员：

```text
releases/<bank-id>/<release-version>/
  bank.qbank.zip
  indexes/<release-id>/wechat/<index-version>/<artifact-revision>.json
  release-envelope.json
```

索引清单增加自己的文件哈希、大小、最低客户端版本、制品修订号；只重建索引时提高制品修订号，题库内容版本保持不变。未来大题库改成分片索引和位置表，也保持相同内容身份。

## 3. 加密需要保护什么

| 需求 | 对应措施 | 能力边界 |
| --- | --- | --- |
| 发现损坏或错误文件 | SHA-256 与文件大小校验 | 哈希不证明发布者身份 |
| 验证发布者、防止内容被替换 | 独立签名的发布清单，客户端内置受信公钥 | 读者持有公钥即可验签，不能伪造发布签名 |
| 下载／存储中的文件保密 | 统一内容包和索引使用认证加密 | 前提是解密密钥不随公开文件一起泄漏 |
| 只有指定读者能得到密钥 | 登录、授权及安全发钥，或线下独立发放高熵密钥 | 具体规则等待下载权限决定 |
| 收回已经离线读过的内容 | 在线复验、许可期限等可限制后续访问 | 无法可靠远程收回已经复制的明文或密钥 |

离线客户端必须能在运行时取得题目明文。即使采用加密，获授权的使用者仍可能截图、调试或提取明文。把同一密钥硬编码在小程序、桌面程序或其资源里，只能增加提取成本，不能用来保证“只有指定读者能读”。这是本项目的威胁模型判断；当前不添加这种形式上的保密功能。

## 4. 建议的后续加密外层

内容先形成标准 ZIP，再在外层使用 **AES-256-GCM** 做认证加密；原始明文包格式保留。GCM 同时提供保密与完整性校验，需正确处理密钥和 nonce；同一密钥下不得重复 nonce。标准依据：[NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)。

拟采用 32 字节随机数据密钥、12 字节 nonce、16 字节认证标签；每个发布制品生成独立密钥，随机值由操作系统密码学随机源产生。索引若含搜索词、题目片段，也必须加密，不能只加密正文却公开索引。若同密钥加密多文件，必须保证 nonce 唯一，并在认证头中绑定文件角色。

拟定外层记录：格式版本、算法、`key_id`、nonce、认证标签和密文长度；认证附加数据绑定题库 ID、内容发布版本、索引格式／制品修订号、文件角色。认证头采用固定字节编码并纳入签名，客户端先限制长度／算法，再验签、认证解密，最后交给 v1 导入器。具体二进制布局和跨端测试向量在实现前固定，当前尚未承诺新的扩展名或生产协议。

发布者身份建议使用 **Ed25519** 对发布清单原始字节独立签名，清单覆盖外层认证头和密文文件的大小、SHA-256。签名私钥仅留在发布端；客户端只放验签公钥。持有对称解密密钥的读者不因此获得发布权限。参考：[RFC 8032](https://www.rfc-editor.org/rfc/rfc8032.html)。

密钥与发布内容分开管理。`key_id` 只是标识，不是密钥；不能从题库 ID、AppID、文件哈希或固定口令推导出公开可算的密钥。若采用口令，必须另选经过评审的口令派生算法、盐和参数；当前不默认采用口令方案。

客户端兼容性需要分别验证：Rust 侧使用维护中的成熟库；微信侧不能假定浏览器 Web Crypto 可用，应选择可运行于微信 JavaScript 环境的实现，固定版本并用已知测试向量验证互通。当前不自写密码算法，也没有未经验证地宣称库已兼容。

本地存储保护另行设计：若解密后长期落盘明文，文件分发加密不会自动保护本机缓存；若改成加密分片和内存按需解密，会影响搜索、密钥保存和性能，需要真机测量。

## 5. 实施顺序与仍需决定的内容

1. 当前交付：三端统一题目源、标准内容身份、小程序内置题库和本地搜索。
2. 用户验收搜索及界面，确认目标设备与题量；内置大题库达到预算上限时，需要分包或后续文件分发。
3. 在权限明确后设计发钥方式、离线授权期限、换机及密钥轮换／吊销策略，再实现三端加密容器读取。旧客户端遇到加密包要明确拒绝或提示升级。
4. 云服务需要时采用腾讯，落实私有文件分发与授权；不在本轮购买资源。
5. 加密交付需验证：错误密钥、认证头篡改、正文／索引篡改、重放旧版本、截断包、断电与磁盘空间不足，以及三端相同明文哈希。任何失败不得切换到不完整题库。

下载权限和密钥发放仍待决定，不影响本轮内置开发。当前没有把“加密”或“发布者验签”标记为已完成。
